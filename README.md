# StudyBot

A retrieval-augmented generation system that answers questions about a corpus of arXiv papers on RAG, with measured retrieval quality and documented failure modes.

Ask it something covered by the papers and it answers from them. Ask it anything else and it says so instead of guessing.

---

## Why this exists

A language model on its own has no access to a specific set of documents, and will often produce a plausible-sounding answer rather than admitting that. This system retrieves the relevant passages first and constrains the model to answer from them.

The interesting part of the project is not that it works, but that it is measured: retrieval quality is evaluated against a held-out question set, the failure modes are characterised, and one architectural change is shown to improve the score.

---

## Architecture

```
INGESTION (run once, when documents change)

  data/*.pdf
    → loader.py      extract text from PDFs
    → chunker.py     split into 300-word chunks, 50-word overlap
    → embedder.py    encode each chunk as a 384-dim vector
    → store.py       persist vectors + text to Chroma


QUERY (every question)

  question
    → hybrid.py      vector search + BM25 keyword search, fused with RRF
    → answer.py      top-k chunks + question → Claude, constrained to the context
    → answer
```

### Layout

| Path | Responsibility |
|---|---|
| `ingestion/loader.py` | Reads PDFs and text files from disk |
| `ingestion/chunker.py` | Splits documents into overlapping chunks |
| `embeddings/embedder.py` | Encodes text as vectors (`all-MiniLM-L6-v2`, local) |
| `vectorstore/store.py` | Chroma persistence and vector search |
| `retrieval/hybrid.py` | Hybrid retrieval — dense + sparse, fused by RRF |
| `generation/answer.py` | Prompt construction and the Claude call |
| `api.py` | FastAPI service — `/`, `/health`, `/ask` |
| `static/index.html` | Chat interface |
| `eval/` | Question generation, curation, and scoring |

Each stage is independent. Swapping the embedding model, the vector store, or the retrieval strategy touches one file.

## Design decisions

**Chunk size — 300 words, 50-word overlap.** Large enough that a chunk contains a complete idea, small enough that its embedding stays specific. The overlap prevents an explanation being severed at a chunk boundary. Both are hyperparameters, not settled values.

**Hybrid retrieval rather than vector-only.** Dense embeddings retrieve on meaning and are weak on exact tokens — dataset names, model names, numbers. BM25 is the reverse. Combining them covers each method's blind spot. Results below.

**Reciprocal Rank Fusion for combining.** Vector distances and BM25 scores are on incomparable scales, so they cannot be averaged directly. RRF ignores the scores and uses only rank position, scoring each chunk as `Σ 1/(60 + rank)` across both result lists. Chunks that both methods rank highly rise to the top.

**Grounding by instruction.** The prompt constrains the model to the retrieved context and specifies an exact refusal string for questions the context does not cover. Describing the desired refusal in prose was not sufficient — the model paraphrased it into a longer explanation. Supplying the literal string fixed it.

## Evaluation

### Method

Thirty questions were generated by prompting Claude with a randomly sampled chunk and asking for a question that chunk answers, with an explicit instruction not to reuse the chunk's distinctive phrasing. Each question is stored with the ID of its source chunk as ground truth.

Scoring measures **retrieval only**, not answer quality. If retrieval fails, generation cannot recover — the correct text was never in the prompt.

- **Recall@3** — how often the source chunk appears in the top 3 results.
- **MRR** — mean reciprocal rank, which rewards ranking the correct chunk higher rather than merely including it.

### Curating the question set

Of the 30 generated questions, 13 asked for citation metadata ("what year was the Phi-3 technical report published?") or a figure from a results table ("what percentage improvement in throughput?"). These test something embedding-based retrieval was never designed to do, and are not questions a reader would put to a study assistant.

They are excluded by `eval/curate.py`, which applies an explicit phrase list committed to the repository so the exclusion can be inspected and disagreed with. Borderline questions that were expected to fail were deliberately kept — filtering out everything that fails would make the number meaningless.

### Results

| Configuration | Questions | Recall@3 | MRR |
|---|---|---|---|
| Vector only, all generated questions | 30 | 30.00% | 22.78% |
| Vector only, curated | 17 | 50.00% | ~34% |
| **Hybrid (vector + BM25 + RRF), curated** | 17 | **58.82%** | **42.16%** |

Increasing `k` from 3 to 5 on the uncurated set moved Recall from 30.00% to roughly 33% — a negative result worth recording, since it showed the missing chunks were not ranked just below the cutoff but were not being found at all. That ruled out the cheap fix and pointed at retrieval strategy instead.

Hybrid retrieval improved MRR proportionally more than Recall, meaning correct chunks are not only retrieved more often but ranked higher.

## Known limitations

**Broad, multi-document questions.** The largest remaining failure category. Questions like "how does the system prevent the model from making up information?" are discussed across most of the eight papers. There is no single correct chunk, but the ground truth names one, so a perfectly good retrieval is scored as a miss. The proper fix is multi-reference ground truth, which requires manual annotation of all 403 chunks — not done here, and the reason is recorded rather than hidden.

**Negation.** Embedding models represent topic well and propositional content poorly. Measured directly on this setup: *"The model predicts the outcome accurately"* and *"The model does not predict the outcome accurately"* score 0.63 cosine similarity despite meaning opposites. Two sentences on the same topic sharing no vocabulary scored 0.58 for comparison. Retrieval is therefore near-blind to negation. Retrieving several chunks and letting generation read the actual text mitigates this, since the model sees the word "not" even when the embedding did not weight it.

**Citation metadata and table figures.** Reference sections compress to nearly identical embeddings, and a table of benchmark numbers carries little semantic content. BM25 recovers some of these; it does not solve them.

**Single-turn only.** No conversation history, so follow-up questions that depend on the previous turn will not resolve.

**No source attribution.** Answers do not cite which paper or chunk they came from, so a user cannot verify a claim without searching the corpus manually.

## Running it

### Setup

```bash
python -m venv venv
venv\Scripts\activate          # Windows
source venv/bin/activate       # macOS / Linux

pip install -r requirements.txt
```

Create a `.env` file:

```
ANTHROPIC_API_KEY=your-key-here
```

### Build the index

```bash
python download_papers.py     # fetch papers from arXiv
python ingest.py              # load, chunk, embed, store
```

### Run

```bash
uvicorn api:app --reload
```

Open `http://127.0.0.1:8000`.

### Docker

```bash
docker build -t studybot .
docker run -p 8000:8000 --env-file .env studybot
```

The image installs the CPU-only build of PyTorch explicitly, before the requirements file is processed. The default PyPI wheel bundles CUDA libraries that a CPU-only container never uses; specifying the CPU index reduced the image from 3.33 GB to 513 MB.

### Evaluation

```bash
python -m eval.generate_questions   # generate a fresh question set
python -m eval.curate               # filter to comprehension questions
python -m eval.score                # report Recall@k and MRR
```

## API

**`POST /ask`**

```json
{
  "text": "What is FAIR-RAG?",
  "n_results": 3
}
```

```json
{
  "answer": "FAIR-RAG is a RAG system that uses an iterative process...",
  "chunks_used": 3
}
```

Errors return the appropriate status code with a message: `400` for empty or out-of-range input, `404` when no documents are indexed, `429` when rate limited, `502` when the model is unavailable, `504` on timeout.

**`GET /health`** returns `{"status": "ok"}` for deployment health checks.

Interactive documentation is available at `/docs`.

## What I would do next

- **Multi-reference ground truth**, to stop scoring correct retrievals as misses on broad questions.
- **Re-ranking** the fused candidates with a cross-encoder before passing them to generation.
- **Source citations** in answers, so claims can be traced back to a paper.
- **Filtering reference sections** during ingestion, removing a chunk category that is never usefully retrieved.
- **Cloud deployment**, so the service is reachable at a public URL.
